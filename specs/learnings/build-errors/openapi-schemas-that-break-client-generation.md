# utoipa and progenitor traps when shaping the OpenAPI schemas

## Context

The specification is generated by utoipa 5.5.0, down-converted to OpenAPI 3.0 by
`@apiture/openapi-down-convert` 0.14.2 (the `generate-oas-30` recipe), and
`bnaclient` is generated from it by `cargo progenitor` (`just generate`).

## Symptom

- A field declared with `#[schema(value_type = Object, examples(...))]` loses
  its examples in the specification.
- A schema of type `[object, string, null]` converts to a 3.0 document that is
  not valid.
- An optional enum (`Option<Enum>`, rendered as `oneOf` with `null`) makes
  progenitor panic in `progenitor-impl` 0.14.0 (`to_schema.rs`), failing
  `generate-client`. Still true in 0.16.0, checked on 2026-11-13: the panic is
  the `todo!("invalid type: {}", typ)` at `to_schema.rs:560`, reached by the
  `type: 'null'` branch of the `oneOf`.

## Root Cause

utoipa ignores the examples next to `value_type`. OpenAPI 3.0 has no type
arrays, and the converter does not rewrite them. progenitor does not handle a
nullable reference: its conversion of a type name handles the JSON types but not
`null`.

## Solution

- Build the schema by hand with `schema_with`
  (`lambdas/src/core/resource/pipelines/schema.rs:107`).
- Express a choice of types with `oneOf`
  (`lambdas/src/core/resource/pipelines/schema.rs:86`, returning `Schema::OneOf`
  at line 103).
- Mark an optional enum `#[schema(nullable = false)]`: it becomes optional
  rather than nullable (`lambdas/src/core/resource/pipelines/schema.rs:186`,
  `lambdas/src/core/resource/cities/schema.rs:318`).

### What `nullable = false` means for the PATCH bodies

The specification then says the field is never `null`, but the API still accepts
it: `PATCH /cities/submissions/{submission_id}` and
`PATCH /pipelines/bna/{pipeline_id}` deserialize the entity wrappers
(`entity/src/wrappers/submission.rs:40`,
`entity/src/wrappers/bna_pipeline.rs:88`), where serde reads `null` as an absent
field, so `null` means "unchanged". The team kept that behavior
(`specs/0005-schemathesis`): the wrappers derive `Serialize` without
`skip_serializing_if`, so a Lambda in another repository that sends one writes
`null` for every unset field, and would break if the API rejected it.
Schemathesis sends `null` there as invalid data, so its
`negative_data_rejection` check is disabled for these two operations, with the
reason (`lambdas/tests/schemathesis.toml:61` and `:65`).

## Prevention

Run `just generate` after any schema change and read the diff of both
specifications; the `bnaclient` CI job fails on any difference.

Revisit the optional enums when progenitor handles a nullable reference: the
specification could then document `null` as "unchanged", and the Schemathesis
check could be enabled again for the two PATCH operations.
