# Requirements Document: Tool Manager for Pinned Command-Line Tools

## Introduction

`just fmt`, `just lint` and the other recipes call command-line tools that
contributors install by hand, at versions pinned in four different places or
nowhere: the `env` block of `.github/workflows/ci-rust.yml` (oxfmt, rumdl,
typos), `bnaclient.yml` (cargo-progenitor), `integration.yml` (hurl, downloaded
with no checksum), and unpinned `extractions/setup-just` steps for just. The
spike in [`spike.md`](spike.md) concluded with a **Conditional Go**: adopt mise,
with explicit `github:` backends, a committed `mise.lock` and
`cargo.binstall = false`, for contributors and for CI. It showed that
`mise install --locked` installs the tools in seconds on macOS and Linux,
verifies the GitHub release attestations of the tools that publish them, and
refuses a tampered archive or checksum; and that an agent in the nono sandbox
can use the tools installed outside it.

This feature makes `mise.toml` and `mise.lock` the one source of truth for the
versions of these tools: contributors install them with one command, CI installs
the same versions from the same files, and the `nono-claude` recipes give agents
access to them.

**In scope**:

- A `mise.toml` pinning oxfmt, rumdl, typos, just, hurl, bacon, sea-orm-cli and
  cargo-progenitor, and a `mise.lock` for four platforms.
- CI installing its tools from these files with `jdx/mise-action` in
  `ci-rust.yml`, `bnaclient.yml` and `integration.yml`, each job only the tools
  it uses, replacing the `env` block, `extractions/setup-just`,
  `taiki-e/install-action` and the `curl` install of hurl.
- The `nono-claude` and `nono-claude-danger` recipes granting agents access to
  the installed tools and putting them on the `PATH`.
- Contributor documentation in `.github/CONTRIBUTING.md`, and `CLAUDE.md`
  pointing at `mise.toml`.

**Out of scope**:

- Installing mise itself: a contributor prerequisite.
- Node.js: the `npx` generators keep using the Node.js on the contributor's
  machine or the runner.
- cargo-lambda, uv, the PostgreSQL client and the Rust toolchain, which keep
  their current installation.
- Automated version bumps (Dependabot, Renovate).
- Changing the contributors' nono profile files: the recipes pass the grants as
  flags.
- Windows, and the other PeopleForBikes repositories (brokenspoke-analyzer may
  get its own spike).
- The project's published documentation under `docs/`.

## Glossary

- **Pinned_Tools**: oxfmt, rumdl, typos, just, hurl, bacon, sea-orm-cli and
  cargo-progenitor.
- **Release_Tools**: the Pinned_Tools installed from a GitHub release archive:
  oxfmt, rumdl, typos, just and hurl.
- **Attested_Tools**: the Release_Tools whose releases carry a GitHub release
  attestation: oxfmt, rumdl, typos and hurl.
- **Crate_Tools**: the Pinned_Tools built from crates.io: bacon, sea-orm-cli and
  cargo-progenitor.
- **Tool_Config**: the `mise.toml` file at the repository root.
- **Lockfile**: the `mise.lock` file at the repository root, generated by mise.
- **Lockfile_Platforms**: `linux-x64`, `linux-arm64`, `macos-arm64` and
  `macos-x64`.
- **Locked_Install**: `mise install` in locked mode, which the Tool_Config turns
  on for every install (the same as `mise install --locked`): it installs
  exactly what the Lockfile records and fails on anything missing from it.
- **Agent_Recipes**: the `nono-claude` and `nono-claude-danger` recipes of the
  root `justfile`.
- **Mise_Directories**: mise's data directory (installed tools and shims), its
  configuration directory and its state directory, at their default locations or
  where mise's own environment variables put them.
- **Trusted_Checkout**: a checkout whose Tool_Config mise trusts, because the
  contributor ran `mise trust` in it or listed a parent folder in
  `trusted_config_paths` in their global mise configuration.

## Requirements

### Requirement 1: One Pinned Tool Configuration

**User Story:** As a maintainer, I want every tool version in one file with a
lockfile beside it, so that a bump is one change that contributors and CI both
pick up.

#### Acceptance Criteria

1. The Tool_Config SHALL pin each Pinned_Tool to an exact version, never a range
   or `latest`.
2. The Tool_Config SHALL name the backend of each Pinned_Tool explicitly: a
   `github:` backend for each Release_Tool and a `cargo:` backend for each
   Crate_Tool.
3. The Tool_Config SHALL turn off mise's versions host, the use of prebuilt
   binaries for Crate_Tools and mise's automatic installs, and SHALL turn on
   locked mode.
4. The Lockfile SHALL record, for each Release_Tool and each of the
   Lockfile_Platforms, the download URL of that platform's archive and its
   checksum.
5. The Lockfile SHALL record the GitHub attestation provenance of each
   Attested_Tool.
6. The repository SHALL NOT state the version of a Pinned_Tool anywhere but the
   Tool_Config and the Lockfile, except the spike and specification documents
   under `specs/` and the release history in `CHANGELOG.md`.

### Requirement 2: Contributor Installation

**User Story:** As a contributor, I want one command that installs every tool at
the pinned version and refuses anything tampered with, so that my machine runs
the same tools as CI without manual downloads.

#### Acceptance Criteria

1. WHEN a contributor runs a Locked_Install in a Trusted_Checkout, the system
   SHALL install every Pinned_Tool at the version of the Tool_Config.
2. WHEN a Locked_Install downloads a Release_Tool archive, the system SHALL
   compare it with the Lockfile checksum before installing it.
3. WHEN a Locked_Install installs an Attested_Tool whose provenance the Lockfile
   records, the system SHALL require that provenance.
4. IF a downloaded archive does not match the Lockfile checksum, THEN the
   Locked_Install SHALL fail and SHALL NOT install that tool.
5. IF the Lockfile has no entry or no checksum for a Release_Tool on the
   contributor's platform, THEN the Locked_Install SHALL fail.
6. WHEN a Locked_Install installs a Crate_Tool, the system SHALL build it from
   crates.io with `cargo install --locked`.
7. IF a command run through mise (`mise exec` or a shim) needs a Pinned_Tool
   that is not installed, THEN mise SHALL NOT install it, and `mise exec` SHALL
   warn naming the tool and the command that installs it.
8. IF a Pinned_Tool is not installed and no other copy of it is on the `PATH`,
   THEN a command run through mise that needs it SHALL fail.

### Requirement 3: Recipes Use the Tools from the `PATH`

**User Story:** As a contributor, I want the `just` recipes to keep calling the
tools by name, so that they work however the tools reach my `PATH` (mise
activation, shims, or a manual install).

#### Acceptance Criteria

1. The `justfile` recipes SHALL call the Pinned_Tools by name, without calling
   mise.
2. WHILE the Pinned_Tools from a Locked_Install are on the `PATH`, `just lint`
   SHALL pass on the repository.
3. IF a Pinned_Tool a recipe needs is not on the `PATH`, THEN the recipe SHALL
   fail with a non-zero status.

### Requirement 4: Agents in the nono Sandbox

**User Story:** As a contributor running Claude in the nono sandbox, I want the
agent to use the tools I installed, so that it can run `just fmt` and
`just lint` without installing anything or reaching the network.

#### Acceptance Criteria

1. WHEN a contributor runs an Agent_Recipe, the system SHALL grant the sandbox
   read access to mise's data and configuration directories and to the mise
   executable on the contributor's `PATH`, and read-write access to its state
   directory.
2. WHEN a contributor runs an Agent_Recipe, the system SHALL put mise's shims
   directory ahead of every directory of the contributor's `PATH` in the
   sandboxed process.
3. WHILE an agent runs in a sandbox started by an Agent_Recipe in a
   Trusted_Checkout, `just lint` SHALL pass using the Pinned_Tools installed
   outside the sandbox.
4. The Agent_Recipes SHALL keep the profile, working-directory and Claude
   arguments they pass today.
5. IF a Mise_Directory does not exist, THEN the Agent_Recipes SHALL still start
   the sandbox.

### Requirement 5: CI Installs from the Same Files

**User Story:** As a maintainer, I want CI to install its tools from the
Tool_Config and the Lockfile, so that CI and contributors cannot drift apart.

#### Acceptance Criteria

1. The `lint` job of `ci-rust.yml`, the `test` job of `bnaclient.yml` and the
   two jobs of `integration.yml` SHALL install their Pinned_Tools from the
   Tool_Config and the Lockfile with `jdx/mise-action`.
2. The workflows SHALL reference `jdx/mise-action` by commit and SHALL pin the
   version of mise it installs.
3. Each job SHALL install only the Pinned_Tools it uses: oxfmt, rumdl, typos and
   just in `ci-rust.yml`; just and cargo-progenitor in `bnaclient.yml`; just and
   hurl in the `integration.yml` job that runs the Hurl tests; just in the
   `integration.yml` job that checks the schema.
4. WHEN a job installs its Pinned_Tools, the system SHALL perform a
   Locked_Install.
5. IF a Locked_Install fails in a job, THEN the job SHALL fail before any step
   that uses a Pinned_Tool runs.
6. The workflows SHALL NOT install a Pinned_Tool by any other means
   (`extractions/setup-just`, `taiki-e/install-action`, `gh release download`,
   `curl`, `apt`).
7. The jobs SHALL keep running the same `just` recipes and checks as today.

### Requirement 6: Documentation

**User Story:** As a new contributor, I want to know how to get the tools and
what they protect against, so that I can set up my machine and my agent once.

#### Acceptance Criteria

1. `.github/CONTRIBUTING.md` SHALL describe the setup: installing mise as a
   prerequisite, trusting the checkout (`mise trust` or `trusted_config_paths`),
   running a Locked_Install, putting the tools on the `PATH`, running the
   Locked_Install again after pulling a change to the Tool_Config (a Pinned_Tool
   that is not installed falls back to any other copy on the `PATH`), and
   logging in with `gh` or setting `GITHUB_TOKEN` to avoid GitHub's anonymous
   rate limit.
2. `.github/CONTRIBUTING.md` SHALL state the system prerequisites mise does not
   install: a Rust toolchain for the Crate_Tools and, on Linux, `libxml2` for
   hurl.
3. `.github/CONTRIBUTING.md` SHALL describe how to bump a Pinned_Tool: change
   the Tool_Config, regenerate the Lockfile for the Lockfile_Platforms, and
   review its URLs.
4. `CLAUDE.md` SHALL point to the Tool_Config for the tool versions instead of
   the `env` block of `ci-rust.yml`.
